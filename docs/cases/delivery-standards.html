Delivery standards · consulting scope

What “ready” has to mean before the commitment grows.

The consulting scope is not limited to defining an AI use case. It also has to define how value will be measured, what evidence is required before release, which non-functional requirements matter, how the system fails safely, and who owns each operating control.

Pilot measurement framework

The pilot must measure business usefulness, not just model performance.

The measurement design is agreed before the pilot so teams cannot redefine success after seeing the outcome.

MeasureEvidence requiredDecision it informs
Incremental fuel impactAgreed comparison method that controls for route, weather, payload, aircraft and operating context.Whether the intervention creates incremental value rather than merely identifying unusual flights.
ActionabilityOperational review of whether each recommendation points to a feasible lever at the required decision time.Whether model output can change an operating decision.
AdoptionAccepted, modified and rejected recommendations with reasons captured.Whether the workflow, explanation and recommendation are usable in practice.
Review productivityComparable cases measured before and during the pilot, while preserving evidence quality and controls.Whether decision support improves the work rather than adding another review layer.
EconomicsRealised benefit, implementation cost, run cost, adoption and sensitivity shown separately.Whether the use case justifies further investment and scale.
Readiness evidence

Release decisions require evidence across model, workflow and controls.

AreaEvidence required before progression
DataTarget definition, point-in-time availability, source ownership, lineage, quality rules and known gaps are documented.
ModelPerformance is compared with the current baseline, reviewed by operating segment, and tested for uncertainty and failure cases.
Decision layerPredictive signals are separated from controllable levers; operational constraints and abstention conditions are explicit.
Agent / workflowTool use, evidence grounding, permissions, human handoff and exception behaviour are tested against realistic tasks.
BenefitsThe measurement method distinguishes estimated opportunity, accepted intervention and verified realised benefit.
OwnershipNamed owners exist for data, model, platform, operating workflow, user support and benefits measurement.
Non-functional requirements in the consulting scope

Latency, availability, auditability and unit cost belong in the programme design.

These requirements affect whether a technically sound solution is usable, supportable and economically viable. They therefore belong in the business and implementation scope—not as engineering details discovered later.

RequirementConsulting questionAcceptance evidence
LatencyHow quickly must the recommendation arrive for the operating decision to remain actionable?End-to-end response tested against the real decision window, including data and dependent services.
Availability & resilienceWhat happens when the AI service, source data or a dependency is unavailable?Fallback process, recovery ownership and service restoration path are tested.
AuditabilityCan the organisation reconstruct why a recommendation was produced and what happened next?Trace links data snapshot, model / agent version, tool outputs, constraints, recommendation, user decision and outcome.
Security & accessWhich users, sources and tools may the system access, and what must always be denied?Role and source permissions are tested before pilot use; protected information is controlled in logs and outputs.
CapacityCan the service operate at the expected volume without compromising the decision deadline?Representative load and backlog scenarios are tested before scope expands.
Unit costDoes the cost per useful recommendation preserve the economics of the use case at scale?Compute, model / agent, data and support costs are included in the value case and monitored during the pilot.
Guardrails and safe failure

Controls have to sit outside the model as well as inside the workflow.

Data validity

Invalid, late or incomplete critical inputs block or qualify the affected recommendation.

Access boundaries

Least-privilege permissions govern retrieval, tools and output destinations.

Operational constraints

Validated services and explicit rules—not free-form model reasoning—enforce hard operating constraints.

Human authority

The user retains the appropriate decision right, with accept / modify / reject and escalation captured.

Change control

Model, agent, prompt, tool or policy changes pass evaluation and approval before production behaviour changes.

Benefits integrity

Estimated, accepted and verified benefits stay separate so the programme does not count model opportunity as realised savings.

Operating controls

Every monitoring signal needs an owner and a response.

Signal familyOwner questionTypical response
Data freshness / completenessIs the decision being made on current, valid information?Investigate source or pipeline; block affected recommendations where required.
Distribution / segment changeHas the operating population moved outside the conditions used for validation?Review by route, fleet, season and operating context; restrict scope if needed.
Model usefulnessIs the output still accurate and operationally actionable?Diagnose model, data and segment effects; evaluate rollback or revalidation.
Agent / tool reliabilityAre tools being called correctly and evidence being preserved?Trace the failing step, stop unsupported completion and restore a known-good workflow.
Operational adoptionAre users accepting, changing or rejecting recommendations—and why?Address workflow, explanation, training, timing or model issues based on rejection reasons.
BenefitsIs measured value tracking the investment thesis?Review attribution, adoption and unit economics before increasing scope.
A monitoring alert that does not lead to a named person taking a defined action is a dashboard, not a control.
